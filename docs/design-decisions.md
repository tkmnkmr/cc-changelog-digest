# 設計判断の記録

なぜこの構成になっているか、という背景情報。実装や手順の変更前に一読すること。

## 情報源に feed.xml を選んだ理由

公式 Atom `feed.xml`（`https://raw.githubusercontent.com/anthropics/claude-code/main/feed.xml`）が
リポジトリ直下に存在し、CHANGELOG.md や GitHub Release と同一コミットで更新される。
検討していた「RSS 案」と「定期確認案」は、実は同じ情報源（この feed.xml）に帰着することが分かり、
追加のスクレイピングや別 API 連携なしで新着検知が実現できた。

feed の `<content>` は `<li>` ではなく `<p>• …</p>` 形式で書かれていることが分かったため、
`check_update.py` の `html_to_text` は両方のパターンに対応させてある。

## 実行基盤にデスクトップのスケジュールタスクを選んだ理由と制約

- **理由**: Claude デスクトップのスケジュールタスクなら、セッションリンクの取得（`get_session self`）
  と Gmail 連携が追加設定なしで使える。GitHub Actions などの CI 基盤を使う場合、これらを
  ゼロから構築し直す必要がある。
- **制約**: Claude デスクトップアプリが起動していないと実行されない（常時稼働ではない）。
  常時稼働が必要になった場合は GitHub Actions + `claude -p` への切り替えを検討する
  （`check_update.py` / `render_png.py` / `publish.py` はスクリプト単体として流用可能）。
- タスク作成ツールにはモデル指定が無く、アプリ既定のモデルを引き継ぐ想定。実行頻度が
  1 日 1 回程度であるため、Opus 系モデルでもコストは許容範囲と判断した。

## 画像を base64 添付でなく Pages URL にした理由

メール添付で画像を base64 埋め込みにすると、送信のたびに数十万トークンを消費する。
GitHub Pages（`site/`）に公開して URL 参照する方式にすることで、メール送信のたびに
発生するコストをほぼゼロに抑えている。

## 「X 投稿文」セクションを廃止し文体の手本とした経緯

初期構成では「X 投稿用の文面」を成果物の 1 つとして生成する案があったが、実際に SNS へ
投稿する運用ではないため、生成物としては不要と判断した。代わりに、X の AI インフルエンサー
投稿が持つ「結論先出し・短文・主語が読者」という文体的特徴だけを執筆規約
（`templates/DIAGRAM_GUIDE.md` の「文体の手本」節）に抽出し、report.html / card.html /
summary.md 全体の書き方の手本として残した。

## 差分検知を「最新既読より新しい版」で判定する理由

当初、差分検知は「既読ゼロなら feed 内の最新 1 件のみを新着とみなす」というロジックで
実装されていた。しかし実際に既読が 1 件登録された直後、feed に含まれる旧版 19 件が
一斉に新規扱いされてしまう不具合が判明した（自動実行の 26 分前に発覚）。

原因は、「既読が 0 件かどうか」で初回判定を分岐させていたため、1 件でも既読が増えた
瞬間に「既読ゼロ」の特別扱いが外れ、feed 内の全件が「未読」として扱われたこと。

対応として、判定ロジックを「feed 内のバージョンのうち、`last_seen.json` に記録された
**最新の既読バージョンより新しいものだけ**を新着とする」方式に修正した（コミット 317a502）。
これにより、既読件数に関わらず一貫した差分検知ができるようになった。
